# Implemented architecture

The [README diagram](../README.md#architecture) shows the running Docker Compose design. React/TypeScript is served by nginx, which proxies same-origin `/api` requests to Spring Boot. The UI supports manual reports, paginated filters, periodic refresh and stored diagnosis/evidence lookup.

Spring Boot commits each incident and `incident.created` JSON outbox row together. A separate non-web Java publisher sends with broker acknowledgement, then marks the row published; unsent rows retain retry/backoff state. The Dockerized Python worker validates events and deduplicates event IDs. Kafka delivery is at least once: acknowledgement/commit failures can cause replay, so no exactly-once Kafka guarantee is claimed. `incidents.raw` and `incidents.analyzed` are initialized legacy/reserved topics, not implemented downstream stages.

Ten Markdown runbooks are chunked and indexed idempotently using local CPU MiniLM embeddings and pgvector. The worker retrieves five chunks and commits receipt, immutable source/content/score snapshots, diagnosis and status in one PostgreSQL transaction. Kafka offsets follow successful persistence or durable quarantine. Processing/quarantine persistence or offset-commit failure stops the worker; restart/replay uses durable deduplication.

Provider `none` stores an explicit RETRIEVAL_ONLY result with original evidence and no generated action sections, normally leaving status RECEIVED. Optional local Ollama uses a LangChain prompt/runnable/parser, structured output and supplied-filename citation checks; successful generation sets DIAGNOSED. Incident and retrieved content are untrusted data. Generated recommendations require human review; citations do not prove semantic correctness, and no tools or remediation executor exist. Model/output failures retry, then quarantine durably and mark still-pending incidents FAILED. Duplicates do not regenerate historical results.

Flyway belongs to the API: V1 incident/diagnosis schema; V2 outbox/receipts/failures; V3 Kafka tombstones; V4 managed corpus/snapshots; V5 diagnosis provenance/legacy labeling; V6 Alertmanager fingerprints, occurrence history and resolved tombstones. Applied migrations and the legacy public.runbook_chunks table are preserved; historical receipts are not backfilled.

Actuator/Micrometer and prometheus_client expose bounded-label metrics. Prometheus scrapes Docker service addresses; Grafana provisions 16 panels. Prometheus sends error/latency/availability alerts to Alertmanager, which delivers firing/resolved notifications to the API. Active fingerprints deduplicate incident/outbox creation; resolved notifications update the occurrence, and delayed worker processing preserves RESOLVED. Internal incident/webhook/monitoring routes are excluded from HTTP error/latency rules to avoid recursion. All components share one host, so this is not an independent external watchdog.

PostgreSQL/pgvector, Kafka and monitoring have persistent Compose volumes. Host PostgreSQL remains localhost:55432; applications use postgres:5432 internally. Optional CPU Ollama has a separate retained model volume and no published host port. Base configuration remains retrieval-only.

Kubernetes/Kustomize, Azure Terraform and Azure DevOps YAML are separate future infrastructure designs. Only static validation/local equivalents have run; no Kubernetes cluster, Azure deployment or organization CI execution is claimed.
